# Theme engine plan (stage 2): every screen a styled element tree

Status: research and spike done; **phase 1 (step B of `V052_PLAN.md`) and phase 2 (step D, section 10: Home and the shared header) built** on the branch `theme-engine`: the production-grade engine in `crates/style` and the paint widget with slots in `crates/app/src/widget/styled.rs`, both behind the cargo feature `theme-engine` (off in every normal build) until step D moves Home onto them (section 9 says exactly what shipped, what differs from this plan and what step D must watch). Recommendation: **go, with limits** (section 7). Context: `CUSTOMIZATION_PLAN.md` section 14 (stage 1, shipped in 0.5) and `V06_BRIEF.md` ("Native layout engine for themes"). No WebView, browser engine, HTML renderer or JS, ever.

## 1. The model

- **Tree.** Each themable screen builds a `Doc` (`crates/style/src/doc.rs`): an arena of elements, parents before children. An element is a NOCTURNE component with a tag (`header`, `nav`, `a`, `section`, `div`, `h1`...), classes (`card`, `thumb`, `row-title`), an optional id and data attributes (`data-kind="movie"`, `data-watched="true"`). Text lives in its own leaf (`div.card-title` with a string), like an anonymous box: a leaf that must be centred inside a flex parent needs a child leaf (`.avatar > .label`). CSS can never add elements; only the app's tree builders can. The tree is built from app state when the state changes, never per frame.
- **Cascade.** Own implementation, about 350 lines (`select.rs`, `cascade.rs`, `props.rs`): selector parser and matcher, rules indexed by the rightmost key (id, class, tag), then per element: matched declarations ordered by `!important`, specificity, source order; `style=""` set by the app for data-driven values (artwork colour, a width) beats selectors; custom properties inherit and `var()` substitutes (depth 8, 4 KB); text properties inherit (`color`, `font-size`, `font-weight`, `line-height`, `text-transform`, `text-align`). The stylesheet is read by the existing `customize` reader (`read_rules`, comments, at-rules, 256 KB and rule limits unchanged), and colours and gradients by the existing `customize::value`. The `selectors` crate (Servo) was not adopted: it needs an `Element` trait impl, brings `servo_arc`, `precomputed-hash` and more, and we need no `:has()` yet. Revisit only if `:has()` becomes a requirement.
- **Layout.** Taffy 0.15.1 (MIT, Rust 1.71, current). Features: `std`, `taffy_tree`, `flexbox`, `grid`, `block_layout`, `content_size`, `parse`; no float, calc, flexbox-balance. `parse` lets Taffy's own CSS reader turn values into its types (`Display`, `FlexDirection`, `AlignItems`, `Dimension`, `GridTemplateComponent` with `repeat(auto-fill, minmax(250px, 1fr))`, `GridPlacement` with `1 / -1` and `span 2`), which removed most of the value-parsing code; it costs `cssparser` (MPL-2.0, already allowed by `deny.toml`) plus `dtoa` and `dtoa-short`; `cargo deny check licenses bans sources` passes. API used: `TaffyTree<NodeId-context>`, `new_leaf_with_context`, `set_children`, `compute_layout_with_measure` with `compute_leaf_layout` for text leaves, `Layout { location, size, scroll_width(), border, padding }`. Taffy has no `order` (children are sorted by `order` before `set_children`, and that sorted list is also the paint and focus order), no `z-index` (separate paint order), no `position: fixed/sticky` (fixed is laid out absolute and painted at a fixed screen place), no inline formatting (a text leaf is one block), and `calc()` needs a callback (left out). Grid template areas exist in Taffy but the spike only supports line numbers (`grid-column: 1 / -1`).
- **Paint.** One custom Iced widget (`crates/app/src/spike.rs`, to become `widget/styled.rs`) walks the scene: quads with solid or linear-gradient backgrounds, per-side borders, one radius, one shadow, opacity (per box, not a group), text through `fill_text` with the shaped font, clipping layers for `overflow`, scroll offsets per container and for the page, culling of subtrees outside the clip. Text is measured by the real shaper (`iced::advanced::graphics::text::Paragraph::with_text`, cosmic-text) behind a cache; the layout needs only the measure callback, so tests use an approximation. Interactive leaves (text inputs, buttons that need keyboard focus, the video hole, virtualised grids) are element slots: the widget gives a slot its Taffy rectangle and hosts a real Iced element there, drawn in tree order. The spike did not build slots; the Hole already works exactly this way (a widget that reports its bounds), so the risk is z-order and focus plumbing, not feasibility.
- **Selectors, realistic:** type, universal, `.class`, `#id`, `[attr]` `=` `~=` `^=` `$=` `*=`, descendant, `>`, `+`, `~`, `:hover`, `:focus`, `:focus-visible`, `:active`, `:first-child`, `:last-child`, `:only-child`, `:nth-child(an+b|odd|even)`, `:not(compound)`, `:root` (all in the spike). To add: `:is()` and `:where()` (cheap, 78 of 950 selectors in ElegantFin use `:is/:where/:has`), `:not()` lists, `::before`/`::after` with `content: "text"` as generated leaf children (bounded), `@media (min-width/max-width/orientation)` evaluated against the window (we own the viewport; ElegantFin has 28 `@media` blocks).
- **Properties, realistic and in the spike:** `display` (flex, grid, block, none), `position` (relative, absolute, fixed), `top/right/bottom/left/inset`, `width/height/min/max` in px, %, rem, em, vw, vh, vmin, vmax, `aspect-ratio`, `margin`, `padding`, `border*`, `border-radius` (one value), `box-shadow` (one), `opacity`, `overflow(-x/-y)` (`auto` means scroll), `flex*`, `gap`, `justify-*`, `align-*`, `order`, `z-index`, `grid-template-columns/rows`, `grid-auto-*`, `grid-column/row`, `background` (colour or linear-gradient, 8 stops), `color`, `font-size`, `font-weight`, `line-height`, `text-transform`, `text-align`, `white-space: nowrap` and `-webkit-line-clamp` (clamp without an ellipsis yet). Planned: `transform` (translate and scale at paint through the renderer transformation, as `widget/zoom.rs` does), `transition` and a bounded `@keyframes` (animate paint properties only, never layout; driven by `window::frames()` only while something animates, reduced motion respected), `font-family` from installed fonts, `letter-spacing` (Iced has no tracking), `outline`, `text-overflow: ellipsis`, `background-size/position` for artwork, `filter: blur()` only on image elements (a pre-blurred bitmap), `grid-template-areas`.
- **Impossible natively, stays that way:** arbitrary HTML, JS, iframes, forms of the web, `@import` and `url()` of remote resources (never fetched), `@font-face`, inline formatting contexts (mixed spans in one paragraph, `float`, tables, `columns`), `backdrop-filter` and general `filter` (Iced has no per-region blur; translucency is the fallback), `mix-blend-mode`, `clip-path`, masks, SVG filters, `position: sticky` beyond the fixed emulation, `:has()` (at least until there is a need), CSS counters. A decision for the maintainer (section 8): theme-local image files.

## 2. How far Jellyfin web themes apply

Measured on ElegantFin (79 KB, the current minified build, fetched read-only; not stored in the repo). The nested layer counts differ from `CUSTOMIZATION_PLAN.md` section 1 because that file counted occurrences and this counts rules after flattening `@media`.

- 690 rules and 950 selectors once `@media`, `@supports` and `@layer` blocks are flattened; the current reader skips those blocks whole (585 rules read).
- Selector syntax the spike parser accepts today: 660 of 785 (84%). Rejected: `:is/:where/:has` (103), pseudo-elements (11), `:not()` lists (11). With `:is/:where`, `:not` lists and `::before/::after`, about 95%.
- Declarations: 621 of 859 plain declarations apply today (72%); 400 more use `var()` and were not checked (colours and sizes, which the engine supports). Rejected most: `transform` 25, `transition` 23, `content` 15, `font-family` 6, `backdrop-filter` 5, `background-size/position`, `outline`, `animation`, `filter`.
- Class names (942 selectors carry a class): 390 (41%) use only classes that have a plausible NOCTURNE element (card family `card`, `cardBox`, `cardScalable`, `cardImageContainer`, `cardFooter`, `cardText`, `squareCard`, `backdropCard`, `portraitCard`; `skinHeader`; `detailImageContainer`, `detailRibbon`, `detailPagePrimaryContainer`, `detailSection`; `listItem`; `emby-button`; `sectionTitle`; `itemsContainer`, `vertical-wrap`; `backdropImage`, `backgroundContainer`; `osdHeader`), another 144 (15%) mix one of them with something we lack. The rest target jellyfin-web only widgets (checkboxes, `actionSheet*`, multi-select, `mdl-slider`, program guide, the login form, `layout-mobile` 81 uses). `layout-desktop`, `layout-tv` and `layout-mobile` appear in 158 selectors: expose them on the root (couch mode is `layout-tv`).
- Verdict: a **compatibility class map is worth it** as aliases on our elements, about 60 classes, with the nesting of the most used component (a card: `a.card.cardBox > div.cardScalable > div.cardPadder + div.cardImageContainer.cardContent`, then `div.cardFooter > div.cardText`) so descendant and child chains hold. Expected visual coverage: 50 to 70% of the intent of variable-driven, restyling themes (ElegantFin: card shape, palette, radius, hover, header, detail layout); low for DOM-shape-driven themes (Finimalism: long descendant chains, `transform` and filters everywhere). Cost: 2 to 3 weeks after the engine phases; a coverage test against a vendored sample (small, hand-written, not a copy of a theme) keeps it honest. Not a blocker; schedule after phase 3.

## 3. Performance

Measured (spike, release build, 16-core machine shared with other jobs, so treat as upper-middle values). Elements are demo cards (6 nodes per card) plus the page shell; stylesheets are the four bundled ones.

| nodes | cascade | layout (approximate text measure) | resize (layout only) |
|---|---|---|---|
| 1,160 | 1.7 to 2.3 ms | 1.5 to 2.1 ms | 1.2 to 1.9 ms |
| 10,250 | 11.6 to 19.8 ms | 12.5 to 18.7 ms | 9.4 to 14.9 ms |

- In the app with the real shaper and a cold cache: the 146-node Home builds in 0.35 ms cascade plus 2.0 ms layout including shaping every string once; 10,250 nodes in 39 to 50 ms once.
- Drawing: 33 to 51 us per frame for the Home (just recording quads and text), 50 to 70 us with 10,250 nodes while the page scrolls itself (culling means the cost follows what is visible, not what exists). GPU time was not measured (the headless session renders in software).
- Idle: 0 CPU ticks in 5 s (Iced redraws only on events); RSS of the whole spike process 302 MB, which is the app's wgpu and font baseline, not the engine.
- Memory per node: `Computed` 656 B, Taffy `Style` 552 B, `Node` 192 B, plus Taffy's own node and cache and the rectangles: about 2 KB per element, 20 MB at 10,000, 2 MB for a 1,000-element screen.
- Design rules that follow: cascade and layout run once per state change and on resize (resize can keep the Taffy tree and only dirty text leaves: `Scene::resize`), cached in the screen; hover and focus restyle only the affected subtree (the spike restyles everything, 2 ms at Home size, which is already acceptable); **style sharing**: memoise the matched-rule result by (tag, classes, attributes, parent computed style), so 10,000 identical cards run the cascade once (the biggest remaining cascade cost is re-parsing the same declaration strings per node; compile declarations to typed values once per rule, expected 3 to 5 times faster, not measured); a theme gets a time budget, 3 overruns of 50 ms switch it off with a banner.
- **Virtualised lists with Taffy.** The Taffy tree holds the structure (page, header, sections, rows) and, for a long list, one *virtual container* leaf: its measure function returns `(width, rows(width) * cell_height)` and the item size comes from the computed style of a prototype item (cascade one representative card: width, aspect-ratio, gap, padding). The widget instantiates real subtrees only for the visible window (a few dozen cards, plus a small margin), cascading and laying them out when the window moves by a row, with style sharing making each new row cheap. This keeps `virt.rs`'s math (scroll offset, rows, scroll-to-focus) and makes it follow CSS-provided cell metrics. A carousel row is the same with one row. Not prototyped; the spike culls by rectangle, which is enough for static trees of 10,000 elements but would not stay under budget for 50,000 library items.
- Budget on the footprint rules: engine on, no theme change: zero extra idle cost; extra binary about 1.1 MB (below); extra memory about 2 MB per visible 1,000 elements.

## 4. Keyboard, couch and accessibility when CSS reorders things

- **Focus follows visual order.** The scene keeps each element's children sorted by `order` (and `*-reverse` flips); Tab and the focus ring walk the focusable elements in that depth-first visual order, not the source order. Arrow keys use spatial navigation on the computed rectangles (nearest focusable whose centre lies in the pressed direction's cone, preferring the same row or column), which is what a grid or a rail needs and works for any CSS layout; the Home model in `app/home.rs` becomes a consumer of the scene instead of keeping its own geometry.
- **Which elements are focusable is the app's decision**, never CSS: the tree builder marks them (`a`, `button`, `input`, cards). CSS cannot make something focusable and cannot hide the focus ring: `outline: none` is ignored; the engine always draws a minimum 2 px ring on `:focus-visible` and a theme may recolour it (`outline-color`, or `--nocturne-focus`).
- **Essential floor.** The app marks a few elements `data-essential` (back, nav, search, settings and account entry, theme reset, player play/pause and seek). After the cascade, an essential element cannot be `display: none`, smaller than 24 px, less than 40% opaque, or positioned outside the window (the engine moves it to the nearest visible place and reports it in the theme warnings).
- **Safe mode.** `nocturne --safe-theme` or `NOCTURNE_SAFE_THEME=1` starts without any user theme; the key chord Ctrl+Shift+0 toggles the theme at runtime and is handled before the tree sees keys; a boot marker that is not cleared by the first drawn frame makes the next start run in safe mode with a banner (a broken theme cannot lock the user out). Settings, the Themes page, Admin and onboarding stay hand-written (section 6), so the reset path never depends on the tree.
- **Screen readers.** Iced 0.14 has no accessibility tree, so nothing regresses; keep an accessible name and role on each element (tag plus text) so a future AccessKit bridge has the data. Contrast warnings stay advisory (as in stage 1).

## 5. Security

- A stylesheet is data. No network (`@import`, `url()`, `@font-face` stay unfetched), no code, no file reads, nothing that spawns; this is unchanged from stage 1. The optional theme-local assets (section 8) are the only proposed exception and are read by the app from the theme's own folder with size caps.
- Limits, existing: 256 KB, 5,000 rules, 50,000 declarations, 500 warnings, 8 gradient stops. Spike: selector 300 chars and 8 parts, one `:not` level, `var()` depth 8 and 4 KB result, text sizes clamped 6 to 200 px, `-webkit-line-clamp` 12, `order` and `z-index` clamped to ±1000, tree 50,000 nodes. To add before shipping: reject `repeat(N)` with N above 100 and more than 256 grid tracks, clamp lengths to ±100,000 px and replace non-finite layout results by zero, at most 4 generated pseudo-elements per element and 2,000 per screen, at most 8 `@keyframes` of 32 steps and 8 properties animating at once, cascade plus layout under a time budget (above), and `catch_unwind` around the build so a panic falls back to the default look (the release profile keeps `panic = "unwind"` on purpose).
- Escape hatches: section 4 (flag, environment variable, key chord, boot marker). The theme file is never executed and cannot change settings, servers or write gates.

## 6. Migration from stage 1

- **Stage-1 parts become classes.** The tree builders emit the stage-1 vocabulary as class names (`.card`, `.card-image`, `.card-title`, `.card-meta`, `.row`, `.row-title`, `.hero`, `.hero-title`, `.hero-meta`, `.header`, `.header-link`, `.header-nav`, `.button`, scopes `.page-home`, `.section-resume`), so a stage-1 selector keeps matching. A built-in default stylesheet (the user-agent sheet, in CSS) reproduces today's look using the same tokens (`--nocturne-*` become custom properties on `:root`).
- **Stage-1 specials become tree data.** `--title-position`, `--row-layout`, `--row-columns`, `--hero-style`, `--header-items`, `.row { display: carousel|grid }` are read by a small translator from the existing `Layout` and applied when the tree is built (a card gets `.title-overlay`, a row `.row-grid` or `.row-carousel`, the hero `.hero-billboard`, a hidden header item is not emitted), then the default sheet styles those classes. Existing themes (including Marquee and Feed) therefore keep working unchanged; the stage-1 tests (`cell_h`, `band_h`, `hero_h`, `HEADER_H`) become the parity oracle for the converted screens: same geometry with no theme.
- **Order of conversion:** Home with the shared header; Library and Search grids; Detail; the player overlay. **Stay hand-written:** Settings, Themes page, Admin (many forms, tables, dialogs), onboarding, Sources and Local folders management, account, Watch together panels, dialogs and pop-overs. They take colours, radii and fonts from the tokens as today, which also guarantees the reset path.
- **Phases** (effort for one developer, rough):
  1. *Engine in the product* (2 weeks). Move the spike into `crates/style` for real (UI-free, depends on `customize` for the reader and values): typed declarations compiled once per rule, style-sharing cache, incremental restyle on hover and focus, limits and `catch_unwind`, `:is/:where`, `@media` on window size, `grid-template-areas`, focus order and spatial navigation from the scene, safe mode. App: `widget/styled.rs` (spike widget plus slots for real Iced elements, proven with a `text_input` and the Hole), virtual container. Tests: selector and cascade unit tests, layout goldens, a limits and hostile-input suite, the coverage corpus. Risks: slot z-order and focus; text measure cost. Files: `crates/style/**`, `crates/app/src/widget/styled.rs`, `crates/core/src/customize/mod.rs` (reader exports).
  2. *Home and header* (1.5 weeks). `app/home_tree.rs`, `app/header_tree.rs`, the default sheet `crates/style/themes/default.css`, the stage-1 translator, Marquee and Feed rewritten as pure CSS next to the spike sheets. Tests: no-theme geometry parity, one test per stage-1 property, the four spike themes as presets. Risks: pixel and motion parity (hover zoom, focus glow), keyboard model replacement. Files: `crates/app/src/app/home.rs`, `header.rs`, `widget/cell.rs`, `theme.rs`.
  3. *Library, Search, grids* (1.5 weeks). Virtualised container with prototype-item metrics; card images (async textures, placeholders as backgrounds). Tests: scroll-to-focus, 5,000-item grid under the frame budget. Risks: image loading cadence inside a dynamic window.
  4. *Detail and player overlay* (2 weeks). Hero, seasons, cast strips, buttons; controls as tree around the Hole slot. Risks: the Hole and the transparent window must not change; the video subsurface stays out of the tree.
  5. *Polish* (1.5 to 2 weeks). `transform` and `transition`, bounded keyframes, `::before/::after`, `content`, the Jellyfin class aliases and `layout-*` classes, an element inspector on the Themes page (hover an element, see its tag, classes, data attributes and matched rules; essential for authors), tree reference docs generated from the builders, the Themes page showing warnings from the new reader.
  6. *Release notes and website* (a few days): theme authoring guide, the gallery of presets.
  Total about 9 to 11 weeks. Phases 1 to 3 are enough for a "Home and Library themes" beta; the maintainer may prefer to ship there (0.7) and leave Detail and the player on stage-1 parts until phase 4.

## 7. Recommendation

**Go, with limits.** The approach is proven: one tree, one cascade, Taffy and one widget produced a billboard streaming look, a video-site look with a grid sidebar, a left rail and a bottom dock from the same element tree, with different stylesheets only (captures below), at about 2.5 ms for a rebuild of a Home-sized tree, 0 idle CPU, 33 to 70 us per frame and about 1.1 MB of binary. Limits: tree builders define what can be styled (no arbitrary elements, no inline text flow); `backdrop-filter`, remote resources and JS are out for good; Settings, Admin and the other form screens stay hand-written; long lists need the virtual container, not one node per item; every theme runs inside a time and size budget with an always-available reset. What the spike did not prove: slots for real Iced widgets, a virtualised 50,000-item grid, transitions, and Jellyfin class coverage beyond counting selectors.

## 8. Open questions for the maintainer

1. Theme-local images: allow `url()` to files inside the theme's own folder (a logo, a billboard texture), loaded by the app with size caps, never from the network? Needed for "look like a streaming service" with a brand image; implies a theme as a folder or zip, not a single `.css` text.
2. Keep keyboard order equal to visual order (differs from the DOM-order behaviour of a browser, deliberate) and accept the essential floor (themes cannot hide back, search, settings, player controls)?
3. Accept the `cssparser` dependency that comes with Taffy's `parse` feature (MPL-2.0, small), or hand-write the value parsing (about 600 more lines, no dependency)?
4. Settings, Themes, Admin and onboarding hand-written for good, or convert them later?
5. Jellyfin class aliases: part of this work (phase 5) or later and community-driven?
6. Release train: 0.6 already holds Seerr and yt-dlp; ship the engine as 0.7 after phase 3, or hold it for 0.8 with Detail and player?
7. Time budget and banner behaviour for a slow theme: automatic switch-off acceptable?

## 9. Phase 1 as shipped (step B)

### What is built

`crates/style` (UI-free, depends on `nocturne-core::customize` for the shared reader and colour values):

- `doc.rs`: the element tree. Beyond the spike: `focusable` (the app's decision, never CSS), `essential` (also exposes `[data-essential]`), `slot` (a real Iced element is hosted at this node), `image` (a replaced element with an intrinsic size), `virtual_list` plus `virtual_proto` (a long list), generated `::before`/`::after` leaves, depth cap 96 and node cap 50,000 (`Doc::dropped` counts what was refused).
- `sheet.rs`: a stylesheet read once. `@media` and `@supports` blocks are read (not skipped): `@supports` is decided at parse time (is the property or `selector()` supported here), `@media` stays a condition on each rule and is evaluated against the window (`min/max-width`, `min/max-height`, `width`/`height`, range syntax, `orientation`, `prefers-*`, `hover`, `pointer`, `and`/`not`/comma lists, nested blocks); `@layer` is flattened; everything else is reported once and cut out before the shared reader sees it. Declarations are compiled to typed `Op`s once per rule (`props.rs`; a value with `var()` is compiled after substitution and memoised); rules are indexed by id, class, tag. Origins: the app's default sheet loses to the user's whatever the specificity; inline `style=""` beats both and only its first rule is read.
- `select.rs`: type, universal, class, id, attributes with `=`, `~=`, `|=`, `^=`, `$=`, `*=` and the `i` flag, the four combinators, `:hover`, `:focus`, `:focus-visible` (its own bit: keyboard focus only), `:focus-within`, `:active`, `:first/last/only-child`, `:nth-child`, `:nth-last-child`, the `-of-type` family, `:empty`, `:root`, `:is()`, `:where()` (zero weight), `:not()` with selector lists, `:has()` with relative selectors (descendant, `>`, `+`, `~`; no nesting), `::before`/`::after`. Limits: 300 characters, 8 compounds in all including nested ones, 3 levels, 16 list members, and a per-element step budget (6,000 visited nodes) so a pathological selector ends as a report instead of a hang; `:has()` is memoised per pass and counted in the same budget.
- `cascade.rs`: ordering by `!important`, origin, specificity, source order; custom properties inherit and `var()` substitutes (depth 8, 4 KB, a cycle is dropped and reported); text properties inherit. **Style sharing**: elements with the same tag, classes, the attributes the sheet's selectors actually read, state flags, inline text, parent style group and (only when the sheet uses structural selectors or `:has()`) position or subtree signature share one computed style object, so 10,000 identical cards run the cascade once. **Incremental restyle**: a hover, focus or active change restyles only the elements it can reach (the changed element, its descendants, following siblings when the sheet has `+`/`~`, everything through the cache when a state pseudo-class sits inside `:has()`); a change that touches no layout property never relayouts, and one that does replaces just those Taffy styles in place. A time budget per pass is checked every 64 elements.
- `layout.rs`, `nav.rs`, `virt.rs`: the `Scene`. Taffy 0.15 layout (flexbox, grid including `grid-template-areas` and `grid-area`, block, absolute, `order`, overflow scroll containers, percentages, aspect ratio, `min()`/`max()`/`clamp()`/`calc()` for lengths with `env()` read as its fallback). `position: fixed` is laid out against the window in its own layer and painted without page or container scroll. Text is measured through a bounded cache (`MeasureCache`) in front of the real shaper; text that needs more than the renderer does (a line clamp with an ellipsis, `letter-spacing`, `nowrap` with `text-overflow`) is broken into lines by the engine (`text.rs`) so layout and paint agree. Focus order is the visual depth-first order (`order`, `*-reverse`); arrow keys use spatial navigation on the laid-out rectangles (same row or column first, then a 45 degree cone); `reveal` scrolls containers and the page to a focused element; `hit_test` honours scroll, clipping, `z-index`, `visibility` and `pointer-events`.
- `virt.rs`: the **virtual container**. The app marks one prototype item; its computed width (or aspect ratio and height, measured in a standalone mini layout when it has captions), margins and the container's `gap` give the cell metrics, so a theme controls the grid with ordinary CSS. Only the rows in or near the view exist as real subtrees (built by the app's `VirtBuilder`, styled through the shared cache, laid out as absolute children); 50,000 items stay at about 400 nodes.
- `engine.rs`: `Engine` holds the app's default sheet, the optional user sheet layered over it, a time budget (50 ms), `catch_unwind` around the user-styled build, a fallback to the default look (then to a bare sheet), notices for a banner, and **safe mode**: `NOCTURNE_SAFE_THEME=1` at start, `Engine::toggle_safe_mode` for the key chord (`SAFE_CHORD`, Ctrl+Shift+0, which the widget handles before any slot sees keys), and automatic switch-off after three consecutive slow or failed builds. `Fonts` (`fonts.rs`) resolves `font-family` lists against the installed families plus families the app registers at run time by name (`Engine::fonts_mut().register(..)`, then `Scene::set_fonts`); fetching font files is the app's job.
- **Essential floor** (`cascade.rs`, `layout.rs`): elements the app marks `essential`, and their ancestors, cannot be `display: none`, `visibility: hidden` or below 40% opacity (the offending declaration is dropped and reported with its selector); an essential control smaller than 24 px gets a 24 px minimum when a theme is active; one that ends up mostly outside the window is moved to the nearest visible place with its subtree. All of it is reported under its own warning kind.
- **Paint-side values** (`paint.rs`, `anim.rs`, `props.rs`): layered backgrounds (a gradient over a colour; gradients with up to 8 resolved stops, `px` stops, double-position stops, 8-digit hex), per-side border widths and colours, per-corner radii, up to four box shadows (outer with spread, inset as edge strips), one text shadow, one `filter: drop-shadow()`, `object-fit` and `object-position`, `transform` (translate in px or per cent of the element, uniform scale, `transform-origin`), `transition` and its longhands with the standard curves and `cubic-bezier()`, `mask-image` and `backdrop-filter` through documented fallbacks, `text-decoration: underline`, `visibility`, `pointer-events`, the `font` shorthand, numeric and keyword `font-weight` (also `bolder`/`lighter`), `font-style`, `font-family` lists, `letter-spacing`, `-webkit-line-clamp`, `text-overflow`. Transitions animate paint only (opacity, transform, colours, backgrounds, border colours); `Scene::tick` is driven by the widget while `Scene::animating()`.
- **Warnings** (`warn.rs`): grouped by kind with a count and the first five examples per kind (essential floor, limits, syntax, selectors, at-rules, properties, values, planned-not-drawn, variables, drawn-through-a-fallback, no-effect), most important first. Browser-only properties (`cursor`, `user-select`, `-webkit-tap-highlight-color`, `color-scheme`, `touch-action`, `scroll-behavior`, `appearance`, `will-change`, `contain`, `scrollbar-*`, `scroll-snap-*`, font rendering hints, ...) are accepted silently as "no effect in a desktop app" and listed last; neither that group nor the fallback group counts as a failure (`Report::failures`).

`crates/app/src/widget/styled.rs` is the paint widget: it draws a `Scene` and hosts slots. A slot is a real Iced element placed at the Taffy rectangle of its node and drawn in tree order inside the clip of its ancestors, so z-order and clipping follow the CSS; hidden or clipped-away slots get a zero-size layout and no events. Proven by `iced_test` (`widget/styled_tests.rs`): typing into a `text_input` slot, a `hole` slot reporting its bounds, hover, press, click and wheel mapped to elements, Tab and arrow keys reaching the page only when the slot did not use them, the safe-mode chord winning over a focused input. The preview (`NOCTURNE_PREVIEW=theme-engine`, feature `theme-engine`, `widget/styled_preview.rs`) runs the bundled themes, a text input in the header, a video-hole slot (`NOCTURNE_ENGINE_HOLE=1`), a virtual library grid (`NOCTURNE_ENGINE_VIRTUAL=10000`), keyboard navigation with the focus ring, and prints timings (`NOCTURNE_ENGINE_STATS=1`); `NOCTURNE_ENGINE_THEME`, `NOCTURNE_ENGINE_CSS=<file>` (reloaded on change), `NOCTURNE_ENGINE_SCROLL_Y`, `NOCTURNE_ENGINE_HOVER=<class>:<n>`, `NOCTURNE_ENGINE_FOCUS_SEARCH=1` (a headless session has no pointer; this focuses the text slot so typing can be tested), `NOCTURNE_SAFE_THEME=1`, `NOCTURNE_SNAP`, `NOCTURNE_PREVIEW_SIZE`. The spike's `theme-spike` feature, `NOCTURNE_PREVIEW=theme-spike` and `NOCTURNE_SPIKE_*` variables are gone (renamed).

Approximate text measure (so these are the engine, not the shaper); the four bundled themes; medians.

- With the real shaper in the preview (release): the first build of the 146-node Home is about 18 ms, almost all of it the one-time font system start-up on the first measurement; a later resize is 0.6 to 2.4 ms. ### Deviations from the plan above

- **Absolute positioning** is relative to the parent box (Taffy's rule), not the nearest positioned ancestor; `position: fixed` is relative to the window. `position: sticky` is laid out as absolute.
- `display: contents`, `inline`, `inline-block`, `list-item` and `-webkit-box` are treated as `block` (`inline-flex` and `inline-grid` as flex and grid): there is no inline formatting.
- `calc()`, `min()`, `max()` and `clamp()` work for lengths in px, em, rem, vw, vh, vmin, vmax and for percentages alone; **mixing `%` with a length is refused** (reported), because the containing block is only known inside Taffy (its `calc` callback is not enabled).
- Taffy has no `order`, `z-index` or fixed layer: handled by sorting children before `set_children` (the sorted list is also the paint and focus order), a separate paint order, and the layer node above.
- The essential size floor applies only when a user sheet is active, so the app's own default look is never altered by it.
- `Iced` draws translation and **uniform** scale only: a non-uniform `scale(a, b)` uses the larger factor, `rotate()`, `skew()` and `matrix()` are reported as planned. Text shadows are drawn as offset copies (five for a blur); `drop-shadow()` is a soft shadow of the image's box, not of its alpha shape.
- `letter-spacing` and clamped or ellipsised text are placed by the engine character by character (Iced has no tracking): no kerning between characters of a tracked line, no complex-script shaping there; plain text is untouched and still shaped by the renderer.
- Font weights map to Iced's nine faces, so `450` draws as 400 and variable-font axes are not used.
- `@keyframes` and `animation` are reported as planned; only transitions are drawn. `@container` is reported unsupported. `url()` is never fetched.
- The boot-marker safe mode of section 4 (a marker file that survives a crash before the first drawn frame) is not built: the environment variable, the chord and the automatic switch-off are.

### Open risks for step D

- **Focus handoff to slots.** The widget reports Tab and arrows the focused slot did not use, but an Iced `text_input` keeps its internal focus when the page moves its own: when the tree focus moves, the app has to `operation::unfocus` (or focus the slot's input id) itself. Pointer clicks into a slot work natively.
- **Per-frame cost with many slots.** Every slot gets a layout node and an `update` call on each event; fine for a handful (header input, video hole, a few controls), not for a slot per card.
- **First measurement is slow** (font system start-up, about 18 ms in release, more cold): build the first scene after the renderer is up (first frame), or warm the shaper at start, to keep the first Home draw inside the budget.
- **Parity.** Nothing in the product uses the engine yet; the default stylesheet that reproduces today's look, the stage-1 translator and the geometry parity tests are step D. Text wrapping differs slightly between the renderer's own wrapping and the engine's line breaking for clamped text.
- **Transitions are driven from the widget's redraw events** (`StyledEvent::Frame`): the app must give each to `Scene::tick` and rebuild the view, or animations stall.
- **Virtual lists**: scroll offsets live in the scene, so wheel and focus movement must go through `Scene::wheel`, `reveal` and `scroll_to_item`; item images load asynchronously inside a window that moves, so step E needs a placeholder policy.
- **Iced test harness**: parallel `iced_test` simulators crashed the process once in a full workspace run (also without the feature, so it predates this work); the new widget tests serialise their simulators.

- Code: `crates/style` (doc, selectors, props, cascade, layout, demo tree, four themes in `crates/style/themes/`), `crates/app/src/spike.rs` (widget and preview, replaced by `widget/styled.rs` and `widget/styled_preview.rs`), small core change: `customize::read_rules`, `customize::value` public, `Decl.important`.
- Spike gaps that phase 1 closed: `transform`/`transition`/`::before`, ellipsis for clamped text, per-side border colours, per-corner radii, hover restyling the whole tree, slots, the window preview being keyboard navigable. ## 10. Phase 2 as shipped (step D): Home and the shared header on the engine

Behind the cargo feature `theme-engine` (still off in every normal and published build). With the feature compiled in, the engine page is used by default; `NOCTURNE_ENGINE_UI=0` shows the hand-written Home and header, which stay in the tree for one release as the fallback.

### What moved to the engine

- `app/home_tree.rs` builds Home (hero, Continue watching, Next up, one Latest strip per library, the "Not showing" note) as a `Doc`; `app/header_tree.rs` builds the header, in the same scene on Home (a `position: fixed` header over the hero, or in flow when the theme says `position: static`) and as a scene of its own on every other page. Classes are the stage-1 vocabulary: `.header`, `.header-brand`, `.header-nav`, `.header-link`, `.header-icons`, `.header-search`, `.hero`, `.hero-title`, `.hero-meta`, `.row`, `.row-title`, `.row-arrows`, `.card`, `.card-image`, `.card-title`, `.card-meta`, `.card-subtitle`, `.card-badge`, `.card-progress`, `.button`, with the scopes `.page-home` and `.section-resume|next-up|latest|tiles` and the data attributes `data-kind`, `data-watched`, `data-source`. Class lists are plain strings, so the Jellyfin aliases of step F are one more `.alias` away.
- `crates/style/themes/default.css` is the default user-agent sheet: today's look from the `--nocturne-*` tokens. `app/engine_ui.rs::sheet_css()` puts the active theme's tokens (colours, radii, page padding) in a `:root` rule in front of it and appends the translator's rules (hover scale and transition of the cards and buttons, focus glow). A user sheet layers over this one as before.
- The stage-1 translator is the tree builders themselves: the resolved `Geo` and `Look` of each strip (the numbers `cell_h`, `band_h`, `hero_h`, the row dims and every part Marquee, Feed and Classic set) become inline styles on the nodes, so every existing theme keeps its geometry and look unchanged. Supported: title position (below, overlay, none), grid and carousel with columns and gap, aspect, width, radius and shadow, caption alignment, episode subtitles, badge and progress parts, row details off, row arrows, no frame, hero billboard, banner and overlay, header position, height, alignment, brand and link icons. Not on the engine, so the hand-written page is used: the library tiles' centred label (server UI mode with `--tile-label: overlay-center`).
- Interactive leaves are slots: history buttons (tooltips), the Libraries and Smart menus (pop-overs), the avatar, the people icon, the source filter and link icons. Buttons and cards are tree elements with click targets. The Hole and the video are untouched (Home has none).
- Keyboard and couch navigation come from the scene: arrows use `Scene::spatial` (visual order, then a 45 degree cone), Tab uses `focus_next`, Enter does what a click does, the page scrolls to the focused band and the strip to the focused card. The hand-written `(row, col)` stays as the focus model of the rest of the app (`focus_media`, the hero follows the focused poster) and is kept in step by the scene's focus.
- Images are nodes (`img.card-img`, `img.hero-img`, `img.hero-logo`) with the decoded `Handle` of the app's image cache; while loading, the card's gradient background is the placeholder (as the hand-written cell).
- Safe mode is one chord, **Ctrl+Shift+0**, plus `NOCTURNE_SAFE_THEME=1`: the paint widget reports the chord and the app runs the same action as its Themes page; Ctrl+Alt+T is gone.
- The shaper is warmed before the first scene; transitions are driven by the paint widget's redraw requests while `Scene::animating()` (equivalent to `window::frames()` only while animating: nothing is requested while idle).

### Engine and widget changes it needed

- **Layout is fractional**: Taffy rounding is off and measured text keeps its exact size (the node measure no longer rounds up), because Iced lays text out at fractional sizes and a page that replaces its widgets has to put the same text at the same pixel. The layout goldens still pass.
- **The paint widget draws in passes.** Iced draws a layer's quads, then its images, then its text, and a later layer is above an earlier one, so a scrim over a backdrop or a badge over a poster disappeared under the image. The widget now paints one layer per image boundary (pass `2k` for what lies between images, `2k + 1` for image `k`), skipping subtrees that have nothing in a pass. A scrollbar thumb like the hand-written pages' is drawn for a page taller than the window.
- A card's focus ring and the engine's mandatory 2 px focus ring would double up: Home's interaction state sets `focus_visible: false` and the default sheet draws its own `.card:focus` and `.button:focus` styles (a user sheet that removes them is still covered by the engine's ring once it is set for keyboard focus).

### Keyboard (headless, same key script through both builds)

Down, Right, Right, Down, Up, Left, Enter (opens the item), Escape (back), by injected keys and by real keys through `wtype` (arrows reach the page through the paint widget). Focus, hero and the page after Enter and after Escape are the same as the hand-written page (0.3 to 0.6 mean difference); after Down then Up the page's scroll offset differs: the hand-written page decides from an offset it has not heard back about yet and keeps the band's bottom aligned, the engine from the real offset and aligns the band's top. Tab walks the visual order. Pointer: hover on a card moves the focus there, the click and the chips send the same messages (no pointer device in the headless session: checked with the scene's own hit tests and the widget's `iced_test` suite, not with a live pointer).

### Performance (`fast-release`, 16 cores shared with other jobs, 516-node Home on the demo library)

| step | cost |
|---|---|
| first build (cascade + layout, shaper already warm) | 2.6 ms |
| rebuild when data or an image arrives (365 nodes) | 0.6 to 1.0 ms |
| focus move that relayouts (5 elements restyled) | 0.9 ms |
| recording a frame (13 images, 27 passes) | 0.2 ms median, 0.3 ms worst |
| idle | no redraw requests, no rebuilds (the root tick does not dirty the scene) |

### What still differs, and the risks for the next steps

- Default-off: the cargo feature stays off until the scrolling quirks below and a live pointer pass are checked; flipping `default = [...]` in `crates/app/Cargo.toml` is the only change.
- Page scroll after keyboard navigation differs slightly from the hand-written page (see above); the strip scrollbar (shown on hover by the hand-written strips) is not drawn, the page scrollbar is.
- The libraries and Smart menus keep their pop-overs as slots, so their text is not themable by CSS beyond the slot's box; the account menu, banners and dialogs are unchanged layers above the scene. No chevrons on an overflowing link strip (it scrolls with the wheel or the focus).
- Tooltips of the Search button are gone (it is a tree element; the icon buttons keep theirs).
- The scene is rebuilt on every message that can change what Home shows (about 40 times while images load); it is cheap, but step E should make image arrival a targeted update.
- Slots cost an `update` call per event each; fine for the dozen the header has, not for a slot per card.
